# 2026-08-04 苹果验证码模型训练与测试备忘录

> 本文记录今天对苹果验证码专用模型的**增补数据续训 → 验证 → 部署**完整流程，作为后续训练/调优的参考。

## 1. 背景与目标

- `captcha_data/labeled/apple/` 标记数据从 **421 张扩充到 945 张**（新增的是通用模型认不出的 hard bad-case）。
- 目标：基于这批新增数据**继续优化专用模型**，提升对困难样本的识别率。
- 设备：Apple M4 Pro（CPU + MPS GPU），要求开启 MPS 与多线程训练。

## 2. 训练框架改造

| 文件 | 改动 | 原因 |
|---|---|---|
| `utils/cache_data.py` | 字符集改为**保序**（旧序保留 + 新字符按字母序追加） | 续训时 fc 输出索引按 charset 顺序对应，`list(set())` 重排会导致索引错乱 |

| `projects/apple_captcha/config.yaml` | `NUM_WORKERS: 4`、`TARGET.Accuracy: 0.7 → 0.85` | 多线程加载；给模型留出提升空间 |

- 重建 cache：**945 张** → train **804** / val **141**（Val 0.15）。
- 字符集未变化（33 字符：`1234579ABCDEFGHIJKLMNOPQRSTUVWXYZ` + 空格），续训安全。
- 从迁移模型 checkpoint `92_1000` 继续训练（MPS + 4 worker，`ExponentialLR(γ=0.98)` 每 200 step 衰减）。

## 4. 训练过程与曲线

- 速度约 **0.9s/step**（瓶颈在 CPU 数据增强，非 MPS），每 epoch 约 44s。
- 训练至 epoch ~165 停止（loss 平台化收敛）。
- 关键观察：
  - **AvgLoss**：0.19 → **0.033**（持续下降）
  - **LR**：0.000941 → 0.0008（指数衰减）

## 7. 已知问题与后续建议

1. **已知难例**：2/B 混淆（如 `2ZUS → BZUS`），新旧模型都错，属数据难点。
2. **数据量是最大杠杆**：继续标记 bad-case 扩充数据集，比调参收益大。
3. **预处理轻微不匹配**：训练 resize 用 PIL 默认 BICUBIC，ddddocr 运行时用 LANCZOS，可把 `load_cache.py` 改 LANCZOS 对齐（轻微收益）。
4. **端到端与纯模型差 ~8 点**：gap_min≥0.08 置信门槛会把低置信苹果图回退到内置模型（漏杀），是设计权衡。
5. **框架停止条件不可靠**：单批 acc 噪声大，建议后续用全验证集评估 + 手动导出（已沉淀工具脚本）。

## 9. 补充：迁移学习的产物是什么模型？

**结论：是深度学习模型（CRNN），属于机器学习的一个子类。**「迁移学习」不是一种新的模型类型，而是**训练方法**（权重初始化方式）的不同。

### 迁移学习 ≠ 模型类型

| | 从零训练 | 迁移学习（本项目苹果模型） |
|---|---|---|
| 权重起点 | 随机初始化 | 来自 ddddocr 预训练 `common.onnx` |
| 训练过程 | 只靠自己标注数据从无到有学 | 在预训练权重基础上**微调** |
| 模型结构 | 完全相同（CRNN） | 完全相同（CRNN） |
| 产物 | onnx | onnx |

两种方式最终构建的是**同一种模型**，唯一区别是初始权重怎么来、要学多少。

### 本项目苹果模型的具体结构

```
输入图片
  → 骨干 CNN（ddddocr_beta：21 层卷积 + hswish + 残差）   ← 特征提取
  → 双向 LSTM（512 隐藏单元）                            ← 序列建模
  → CTC 解码 + fc 输出层（34 类 = 33 字符 + blank）        ← 对齐字符
```

- 迁移时：骨干 + LSTM 权重**直接载入** `common.onnx`（`transfer_pretrained.py`），只把 fc 输出层重置为 34 类，然后用标注的苹果验证码做**监督学习**（CTC 损失 + SGD/Adam 反向传播）微调。
- 训练完导出 `apple_captcha.onnx` + `charsets.json`，运行时走 onnxruntime（经 ddddocr 引擎或 `CaptchaRecognizer`）逐图推理。

### 一句话总结

迁移学习产出的**就是模型**，而且是「通用 ddddocr 的微调专用版」——本质上是同一个 CRNN，因为初始权重来自在海量验证码上预训练的通用模型，所以只需少量标注数据就能在苹果难样本上达到 ~0.96 验证集 / ~0.89 批跑匹配率。它和通用 ddddocr 的区别不是「模型类型」，而是「**专精**」：针对某一类验证码微调过。`models/apple_captcha.onnx` 是标准 ONNX 模型，任何 onnxruntime 都能加载推理。

## 10. 补充：字符集改为数据驱动（fc 输出维度收敛）

> 背景：训练页「准备数据」时字符集原本**写死在 `config.yaml`**（34 类），但苹果数据里 `1/2/5/I` 等字符从未出现，白白占用 CTC softmax 类别。本优化把字符集改为**由标记数据统计自动决定**，配置无需手动维护。

### 数据统计结论

- 标记数据扩充到 **2355 张**（2026-08-05），实际出现字符 **29 个**：`3479ABCDEFGHJKLMNOPQRSTUVWXYZ`。
- `0-9 A-Z` 范围内从未出现的字符：**`012568I`**（7 个）。
- `O` 仅出现 12 次（频率极低但非零，**必须保留**，否则已标注样本解码不到）。
- 原 34 类字符集中有 **4 个死字符**：`1、2、5、I`。

### 改动

| 文件 | 改动 | 原因 |
|---|---|---|
| `captcha_trainer/utils/cache_data.py` | 字符集由标记数据统计驱动：**只保留真实出现的字符**（自动丢弃死字符）、保留字符原顺序 + 新字符按字母序追加、非 Word 模式首位保留空格(CTC blank)；丢弃时打 warning 提示旧 checkpoint 不兼容 | fc 输出维度收敛到真实字符数，减少 CTC 对不存在字符的类别浪费/幽灵混淆；保序保证续训 fc 索引稳定 |
| `captcha_app/trainer_engine.py` | `_do_prepare` 改为 **cache 先跑、迁移初始化在其后** | 迁移 checkpoint 的 fc 维度必须用数据驱动后的新字符集构建，否则与训练 Net 输出维度不匹配（34 vs 30 会 load 失败） |

### 效果

- `prepare`（迁移+重置）后 `config.yaml CharSet`：**34 类 → 30 类**（29 真实字符 + blank），fc 输出维度 34→30。
- 迁移初始化 checkpoint 的 `fc.weight` 形状 = `(30, 1024)`（与训练 Net 匹配，验证通过）。
- 重训在 **step 1450 / epoch 23** 早停（单批验证 acc 1.0 > 0.93），导出 `apple_captcha_1.0_23_1450_2026-08-05-19-39-23.onnx` + 30 项 `charsets.json`（`O` 保留在 index 18）。
- ⚠️ **待观察**：本次全验证集 `final_acc = 0.8523`，低于 34 类旧模型的 0.9688——本次在单批噪声 1.0 上提前停训、epoch 仅 23，训练可能不足；字符集收敛本身不应降精度，后续建议拉长 MAX_STEP 重训对比，确认 0.8523 是早停所致而非字符集问题。

## 11. 补充：识别管线性能优化（快路径 + 去重）

> 背景：`recognize()` 默认管线每张图跑 **20+ 次 onnx 推理**（9 预处理变体 × 2 模型 + 逐字符 + 自定义），apple 批跑实测 **~490ms/张**。工作台批跑几百张是常态，提速收益直接。本优化在**不改变识别语义**的前提下砍掉冗余推理。

### 性能画像（cProfile，无模型默认管线 480ms/张）

| 成本 | 占比 | 说明 |
|---|---|---|
| onnx 推理 | **44%**（142 次调用 0.22s） | 9 变体 × beta/std + 逐字符 + 自定义 |
| 噪点检测 | **30%**（0.15s） | `detect_noise_blocks` 纯 Python 子矩形搜索 O(bh²·bw²)；且 `repair_noise_blocks` 内部**重复检测一次** |
| 彩色去噪 | 13% | 5 个变体各自 `fastNlMeansDenoisingColored` |

### 改动

| 文件 | 改动 | 原因 |
|---|---|---|
| `src/api.py` | 抽取 `_run_custom_model()` 统一自定义模型推理；`recognize()` 选中模型时**先跑一次推理**，命中即短路返回：`no_fallback` → 直接返回模型结果；`gap_min≥CUSTOM_GAP_MIN` → 直接返回（快路径），否则走完整管线复用该推理结果 | 模型确信（本类别图）时内置多变体投票只会是同样答案 + 冗余候选，是最重的成本（每图 20+ 次推理） |
| `src/api.py` | 删除 `use_custom` 分支死代码、重复 `custom` 计算；快路径加 `save_preprocessed is None` 护栏 | 保 `-o` 落盘契约；无模型默认路径行为完全不变 |
| `src/preImg.py` | `repair_noise_blocks()` 增加 `blocks` 可选参数，api.py 传入已检测的 blocks | 消除重复 `detect_noise_blocks`（每图省 ~50ms） |

### 效果（实测，2026-08-05）

| 路径 | 优化前 | 优化后 | 加速 |
|---|---|---|---|
| apple 批跑（默认，带 gap 门槛） | ~490ms/张 | 快路径 2.4ms/张、回退 313ms/张，100 张平均 18ms | **~27x** |
| apple 批跑（不回退 ddddocr） | ~490ms/张 | **2ms/张** | **~245x** |
| 无模型默认管线（单张） | 483ms | 411ms | -15%（噪点去重） |

- 工作台实测 100 张批跑：默认模式 1.8s（93/100 匹配）、不回退模式 0.2s（98/100 匹配）。
- 快路径候选列表仅含模型结果（`原图(自定义)`/`自定义`），`text`/`confidence`/`length` 与旧管线完全一致；回归验证 0 失败，测试样例 `xf4y4`/`kdqu`/`phhxx`/`9tns3` 不受影响。

### 评估后放弃的方案

- **`detect_noise_blocks` part2 向量化**：曾写 numpy 版原型，全数据集 2361 张有 **593 张**检测结果不同（float 舍入 + 平局扫描序语义差异），会改变「噪点修复」候选 → 可能改变识别结果。回归风险远大于 ~8.5% 收益（默认管线 411→~350ms），**弃用**，保留原始算法。

> 注：8800 工作台服务器需重启才加载后端改动（快路径）；前端刷新不加载 Python 代码。

## 12. 补充：训练效率审计（2026-08-06）

> 目标：检查模型训练功能是否有可优化、可提效的空间。用 `captcha_trainer/bench_train.py` 实测
> （只读 cache，不写 checkpoint），结论：**训练循环已近效率极限，MPS 是 CPU 的 ~10.6 倍**，无低风险提效空间。

### 实测数据（M4 Pro，torch 2.x + MPS）

| 环节 | 耗时 | 说明 |
|---|---|---|
| MPS 完整前向 | 6.3 ms/批 | CNN 4.7ms + LSTM 1.7ms + fc |
| MPS 整步（前+反+step） | **32.0 ms** | backward 占 ~25ms（小张量反向开销主导） |
| CPU 整步（8 线程） | 339.6 ms | MPS 快 **~10.6x** |
| 数据加载（读图+增强） | ~16 ms/批 | 顺序执行，约占整步一半 |
| 整 epoch（62 步） | **2.0 s** | **32.3 ms/step，30.9 step/s（~950 img/s）** |

> 对比备忘 §4 记的 **0.9s/step / 44s每epoch 已过时约 28x**（那时是旧 torch/旧环境下的数字）。
> 现在**计算是主导、数据加载已不是瓶颈**，且 MPS 本身远快于 CPU。

### 评估过的方案与结论（含放弃项）

| 方案 | 结果 | 结论 |
|---|---|---|
| `NUM_WORKERS>0` | macOS spawn 每个 worker 重新 import 主模块（工作台 server.py），后台 daemon 线程内起多进程直接崩溃 | **不可行**；前端提示「建议 0」是对的。备忘 §2 说 NUM_WORKERS:4 有效是 CLI 主线程场景 |
| 进程内预取线程（生产线程重叠加载与 MPS 计算） | 实测仅 **1.06x** | PIL/numpy 增强被 GIL 束缚、与训练线程竞争；训练本就跑在后台线程，再加线程风险大于收益，**放弃** |
| 增大 batch size（32→64/128） | 吞吐仅 +7%~+10% | MPS 小张量 per-op 开销占比低，计算随 batch 近似线性；且大 batch 改变收敛行为，**不是有效杠杆** |
| 一次性操作 | checkpoint 保存 59ms / 全验证集评估 2.1s / ONNX 导出 0.2s | 均正常，无需优化 |

### 落地修复

- **`captcha_trainer/utils/load_cache.py`**：`LoadCache` 加载时过滤 cache 中引用**已不存在图片**的条目
  （标记数据增删后 cache 过期），避免每 epoch 反复报缺失错误 + 无效样本空占 batch 位。
  本次实测 cache.train 2002→2001、cache.val 353→352（各 1 条过期）。每个 loader 只警告一次。
- **`captcha_trainer/bench_train.py`**：新增训练效率基准脚本，供 torch 升级 / 换机后复测。

### 结论

- 训练效率瓶颈在 **MPS 计算本身（backward ~25ms）**，已是最优设备路径；想再快只能走
  数据量 / 模型结构 / 多机并行，属训练效果范畴，非效率范畴。
- 数据加载约占整步一半，但受 GIL 限制无法用进程内线程重叠，多进程又因 spawn 冲突不可用，
  属于架构约束下的「现状最优」。
- 若追求更高吞吐，唯一现实选项是**换更大 batch 配合更高 LR 并调参**，但收益仅 ~10% 且需重调收敛，
  不建议仅为此改动。
